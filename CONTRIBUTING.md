# Contributing Guidelines

This document describes how our group works on the AEGIS course project. All members should read it before making changes to the repository.

## 1. Git Workflow

1. Update your local `main` branch: `git checkout main`, then `git pull`.
2. Create a branch for your task: `git checkout -b feature/<task-name>`.
3. Commit your work in small steps.
4. Push the branch and open a pull request on GitHub.
5. Ask at least one group member to review the pull request.
6. Merge with **Squash and merge**, then delete the branch.

Do not push directly to `main`.

## 2. Branch Names

Use `<type>/<short-description>`, lowercase, with words separated by hyphens.

| Type | Purpose | Example |
|---|---|---|
| `feature/` | New hardware, firmware or application feature | `feature/pwm-generator` |
| `fix/` | Bug fix | `fix/spi-timing` |
| `docs/` | Documentation and report material | `docs/register-map` |
| `test/` | Testbench only | `test/fifo-corner-cases` |
| `chore/` | Repository setup and configuration | `chore/repository-standards` |

## 3. Commit Messages

We follow the [Conventional Commits](https://www.conventionalcommits.org/) format: `<type>(<scope>): <short summary>`.

- Write in English, in the imperative mood (`add`, `fix`, `update`), lowercase, with no period at the end.
- Keep the summary under 50 characters.
- Types (defined by the Conventional Commits standard): `feat`, `fix`, `test`, `docs`, `refactor`, `build`, `chore`.
- Scopes: `adc`, `averager`, `fifo`, `pwm`, `fault`, `top`, `system`, `firmware`, `application`, `documentation`.

| Example | Meaning |
|---|---|
| `feat(adc): add LTC2308 SPI controller` | New feature in the ADC interface |
| `fix(pwm): latch duty at period start` | Bug fix in the PWM generator |
| `test(fifo): add full and empty test cases` | New test cases for the FIFO |
| `docs(documentation): add register map` | Documentation change |

## 4. Naming Rule

Write every name in full words, in documents and in code. Do not abbreviate.

| Write | Do not write |
|---|---|
| `counter` | `cnt` |
| `iClock` | `iClk` |
| `controller` | `ctrl` |
| `THRESHOLD_HIGH` | `THR_HI` |
| `pull request` | `PR` |

Allowed exceptions:

- Standard technical acronyms: ADC, SPI, PWM, FIFO, I2C, JTAG, UART, LED, OLED, SoC, IP, RTL.
- Pin names from datasheets and board manuals: `CONVST`, `SCK`, `SDI`, `SDO`, `CLOCK_50`, `LEDR`.
- The `_n` suffix for active-low signals and the `tb_` prefix for testbench files.
- Keywords defined by a standard, such as Conventional Commits types.
- Names generated by tools (`aegis_app`, `aegis_app_bsp`, Platform Designer port names) and menu labels of tools.
- The conventional directory names `docs` and `rtl`.

## 5. Verilog Guidelines

- One module per file. The file name matches the module name.
- Input ports start with `i`, output ports start with `o` (`iClock`, `oPwm`).
- Active-low signals end with `_n` (`iReset_n`).
- Use one clock (50 MHz). Do not create new clocks with counters; use enable signals instead.
- Reset is asynchronous and active-low: `always @(posedge iClock, negedge iReset_n)`.
- Use `<=` in sequential blocks and `=` in combinational blocks.
- Use `parameter` or `localparam` instead of fixed numbers.

## 6. Simulation

- Each module in `rtl/` has a testbench `simulation/tb_<module>.v` and a script `simulation/run_<module>.do`.
- Testbenches check results automatically and print `PASS` or `FAIL` for each test case.
- A module is complete only when all test cases pass.
- Save important waveform screenshots in `docs/simulation/` for the report.

## 7. C Firmware Guidelines

- Put spaces only around `+` and `-`. Do not put spaces around `*`, `/`, `=`, `==`, `<`, `>`.
- Always use braces `{}` for `if`, `else`, `for` and `while`, even for one line.
- Use the macros in `aegis_data_acquisition_controller_registers.h` instead of raw register offsets.
- Follow the naming rule in section 4 and write comments in English.

## 8. Files Changed by Tools

Quartus and Eclipse modify some files automatically. Before committing, run `git status`. If one of these files is listed and you did not change it on purpose, discard the change with `git checkout -- <file>`.

| File | Changed by |
|---|---|
| `hardware/quartus/aegis_top.qsf` | Quartus |
| `hardware/quartus/software/aegis_app/Makefile` | Eclipse |
| `hardware/quartus/software/aegis_app_bsp/settings.bsp` | Eclipse |

## 9. Shared Project Files

Only the member in charge of system integration edits `hardware/quartus/aegis_system.qsys` and `hardware/quartus/aegis_top.qsf`, to avoid merge conflicts. If you need a change in these files, open an issue and assign it to that member.

## 10. Editing Markdown Files

Edit `.md` files with Visual Studio Code or another plain-text editor. The Markdown formatting mode of Windows 11 Notepad inserts backslashes (`\#`, `\-`) and breaks the files.

## 11. Before Opening a Pull Request

- [ ] Your branch is based on the latest `main`
- [ ] Simulation passes (write the result in the pull request, for example `9 PASS, 0 FAIL`)
- [ ] Waveform screenshots are attached for new modules
- [ ] `docs/` is updated if registers or interfaces changed
- [ ] `CHANGELOG.md` is updated under `[Unreleased]`
